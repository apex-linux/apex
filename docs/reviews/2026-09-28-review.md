## 1. Verdict

Keep the substrate. Change the product.

- **The substrate is right.** bootc on the ostree backend with composefs, the
  digest-pinned `fedora-bootc:45`, `build-rootfs` with explicit lists and exclude guards,
  rechunking, the legacy gate and integer scale 2 are sound. The image composed and
  installed in the builder VM on 2026-09-24. Integer scale 2 gives exactly the mockup's
  1440×900 stage, which makes pixel-exact work possible.
- **The owner's defining requirement does not exist.** The desktop is stock GNOME 51
  plus five vendor defaults in four schemas (`90_apex.gschema.override:9-32`). No
  designed surface is built or planned before M3. ADR 0011 forbids the Settings panel,
  the window radius, the icon theme and GDM theming, and puts all shell work in an M3
  extension.
- **Most effort went to update, boot and CI machinery.** About 52K lines of Rust (17K
  production) serve updates, boot assessment and hardware tooling. About 9.3K lines of
  shell and YAML are checks, tests and CI. None of it serves the mockup. Part of it
  serves the hardware goal, but no hardware fix has shipped. The update stack is well
  built and 3 to 5 times heavier than one laptop needs.
- **Neither hardware complaint is fixed.** The speakers ship as `degraded=audio` with no
  measurement taken. The fingerprint patches let enrollment finish on a pipeline that
  is not known to verify on this sensor.
- **Nothing is committed.** About 80K lines exist only as an untracked working tree,
  with no remote. No GitHub workflow has ever run.

The plan:

1. Commit the tree as it is and push it to a private remote today. Nothing changes
   before that.
2. Replace ADR 0011 with ADR 0014, "overlay first". gnome-shell, mutter, libadwaita and
   GTK stay Fedora-signed. gdm does too, unless the owner takes the optional spec-only
   rebuild. Apex reaches the mockup with a compiled shell theme, two small first-party
   extensions, a vendored Dash to Dock, a user-CSS window radius, and two small rebuilt
   packages: gnome-control-center with 3 patches and nautilus with 1.
   Answered (§5.3): a rebuilt gnome-shell is the primary mechanism instead, and the
   §8 details are built now. ADR 0015 adds the CachyOS kernel and the NVIDIA modules.
3. After acceptance, freeze the update and boot stack as the safety net and cut the
   ceremony around it (§4).
4. Spend about three hours on the laptop: the speakers, the fingerprint score test and
   an s2idle baseline.
5. Build the Apex look first. The Apex theme shows in the desktop VM at the end of
   roadmap S1a (target 2026-10-23). The laptop boots Apex from the USB SSD in S1c
   (target 2026-11-20).
   Answered (§5.3): the revised roadmap shows the Apex theme at the end of S1b (target
   2026-11-13) and boots the laptop, with the CachyOS kernel and NVIDIA, at the end of
   S1d (target 2026-12-11).

## 3. What changes

Each finding has an ID, its severity after verification, the evidence, the impact and
the change. "Review" notes where the adopted change differs from what a reviewer or
verifier first proposed.

### 3.1 Direction and policy

**A1. No designed surface exists, and the roadmap schedules the design last.**
Critical.
- Evidence:
  - The only desktop customisation is five vendor defaults
    (`90_apex.gschema.override:9-32`), one of them the dark style.
  - The repo has no `.css`, `.scss`, `.js`, `.ui`, `.svg` or font file outside the
    mockup.
  - M1 needs image and qualify workflows green, promotion and full acceptance before
    any UI (`docs/ROADMAP.md:25-38`).
  - `docs/ROADMAP.md:45-60` plans an Updates app, a Tweaks page and, at M3, one
    extension. No document mentions the mockup.
- Impact: the owner's main deliverable has no build path, no acceptance test and no
  date. The first image would be stock GNOME in dark style.
- Change: ADR 0014 and the roadmap, ordered by what the owner sees. The desktop comes
  first.
- Review: the mockup is an interactive HTML prototype in `design/mockup/`.
  `just design-render` renders its screens, light and dark, into `design/renders/` with
  `tools/design/render-mockup.cjs`: 33 files, git-ignored, about 32 MB, with no
  duplicates. They are a human reference, never a pixel gate.

**A2. ADR 0011 forbids most of the mockup's engine work.** Critical.
- Evidence: ADR 0011:27 refuses Shell themes, gtk.css, icon-theme swapping and a patched
  gnome-control-center. `docs/ARCHITECTURE.md:31-32` limits customisation to supported
  APIs; `:39-40` lists custom themes and forks as non-goals.
- Impact: the Apex Desktop panel, the window radius, the icon theme and the greeter
  cannot ship. Shell restyling waits for an M3 extension, and every design change
  becomes an ADR argument.
- Change: ADR 0014 supersedes ADR 0011. It amends ADR 0002, ADR 0007:25-29, and
  ARCHITECTURE goal 6 and non-goals.
- Review: only ADR 0011:12 is factually wrong. libadwaita has no theme API and
  gnome-control-center has no panel API; both facts are true, and ADR 0014 is built
  around them. A JSON session mode cannot carry the design. A mode named like a built-in
  one is ignored (`sessionMode.js:109-110`), and JSON modes exclude the unlock dialog
  (`:122`).

**A3. About 80K lines are uncommitted, with no remote.** High.
- Evidence: `git log` shows no commits; `git remote -v` is empty. `.github` holds 6,074
  lines that never ran.
- Impact: one wrong command loses everything. There is no baseline to bisect against
  once engine work starts.
- Change: commit the tree as it is, tag `baseline-2026-09-28` and push to a private
  remote before any file changes (roadmap S0). Turn GitHub Actions off for the new
  repository before the first push. Otherwise `image.yml` starts on push and calls a
  build that may run 330 minutes, and `privacy-guard.yml` fails on the mockup (§6).
- Review: the local path has run. `build-rootfs` and `install_disk` succeeded in the
  builder VM on 2026-09-24. Only the GitHub side is unproven. The builder VM's rsync
  copy is not a backup.

**A4. "Rust or Go" cannot cover the desktop's layers.** Low.
- Evidence: ADR 0002:17-21 allows only a TypeScript extension and C patches.
- Impact: pressure to force Rust through FFI into gnome-control-center or the shell.
- Change: the language rule in ADR 0014. Rust for daemons, agents and tools; GJS in the
  shell; C with Blueprint in gnome-control-center and nautilus; C for kernel and
  libfprint patches; SCSS for themes; Bash for build glue. No Go.

**A5. The mockup's "Apex Fedora" brand conflicts with Fedora's trademark.** Low.
- Evidence: html:487, 540, 700. The repo already avoids Fedora trademarks
  (`image/packages/base.txt:119-122`, `os-release:14-22`).
- Impact: published images named "Apex Fedora" would break Fedora's trademark rules for
  remixes.
- Change: owner decision 19. Recommended: the product is "Apex", with "Built on Fedora
  Linux 45" as attribution. A diamond logo SVG becomes `LOGO=`.

### 3.2 Desktop layer

**B1. There is no shell architecture.** High.
- Evidence: the ADRs plan one extension (ADR 0011:26, ADR 0002:20). Most of the mockup
  is stock GNOME 51 structure: Quick Settings, the calendar popover, the overview and
  the app grid need only styling. New structure: the dock, the focused-app name, the
  search button and popup, the solid-when-maximised bar, the single-stage lock.
- Impact: without a map the work either over-patches or ships an extension that breaks
  at every release.
- Change: ADR 0014's per-component table. The shell stays a Fedora binary.
  - A compiled theme gresource themes the session, the lock screen and GDM from one
    file.
  - `apex-shell` (at most 4 overrides, all allocated) and `apex-lock` (2 overrides) add
    behaviour.
  - gnome-shell enters the rebuild lane only under the escalation rule.
- Review: several lenses proposed a patched gnome-shell. The overlay was chosen because
  it keeps Fedora's signature, falls back to stock when an extension fails, and costs
  far less per release. The patched shell stays as the escalation path.
- Answer 1 (§5.3): the alternative. gnome-shell is rebuilt from the Fedora SRPM and is
  the primary mechanism. apex-shell and apex-lock move into the package as an in-tree
  layer with a stock fallback per hook. Apex ships no extensions (ADR 0014).

**B2. Flatpak apps escape any libadwaita change.** High.
- Evidence: Bazaar and Firefox are Flatpaks (`apex.preinstall:14-20`). Flatpak apps use
  the runtime's libadwaita.
- Impact: two visual tiers.
- Change: app chrome keeps libadwaita's palette, so only the radius differs. The radius
  comes from `--window-radius` in a user CSS file, exposed to Flatpaks read-only. A
  Bazaar spike in S1b confirms it. Every app shown in the mockup except Software ships
  as an image RPM. Software is Bazaar, a Flathub app with no Fedora package, so its
  corners depend on the spike.
- Review: Firefox is not a libadwaita app, so only Bazaar is affected today. The
  verifier proposed libadwaita's colour variables as the main channel. This plan keeps
  libadwaita's palette instead (B14), so only `--window-radius` goes in user CSS.

**B3. The design tokens exist only inside the mockup.** Medium.
- Evidence: the `TH` table (html:504-507) holds about 33 properties per theme, used in
  223 `var()` references. Radii, blur and motion are literals.
- Impact: values get hand-copied and drift.
- Change: one hand-written `desktop/tokens/_apex-tokens.scss` from `design/SPEC.md` §2.
- Review: a Rust token generator with golden tests would repeat the audio renderer's
  weight. Add a generator only when a third consumer drifts.

**B4. Shipped defaults contradict the mockup.** Medium.
- Evidence: `color-scheme='prefer-dark'` (override:11) against the mockup's light
  default (html:550); five favourites against nine (override:26, html:515); no
  `button-layout`, battery percentage, weekday, monospace font, icon theme or wallpaper.
- Impact: the first login shows a dark desktop, another dock and close-only title bars
  before any design work starts. These are the cheapest gaps to close.
- Change: the rewritten override in `design/SPEC.md` §6.3. Light is the default, as
  drawn.
  - GNOME Shell 51 draws a light shell only for `color-scheme='prefer-light'`
    (`main.js:437-452`). Every session mode inherits `prefer-dark`
    (`sessionMode.js:25`).
  - The stock Dark Style toggle and Settings > Appearance write `'default'` for light.
    That gives a dark shell over light apps.
  - apex-session-agent therefore rewrites `'default'` to `'prefer-light'`.
    gnome-control-center patch 0002 maps Appearance's Default toggle to
    `'prefer-light'`.
- Answer 1 (§5.3): a `sessionMode.js` hook in the rebuilt shell draws a light shell for
  `'default'`. The agent's rewrite and the gnome-control-center mapping are dropped,
  and the override sets no `color-scheme`.

**B5. The Settings surfaces need a patched gnome-control-center.** Medium.
- Evidence: the Apex Desktop panel comes first in the sidebar (html:539, 685), with
  coloured tiles (html:705) and a "Software Updates · 3 updates available" row in
  System (html:700). Panels are compiled in (`shell/cc-panel-loader.c:86-119`,
  `cc-panel-list.c:336`). Stock shows the updates row only with gnome-software, which is
  excluded.
- Impact: the mockup's first Settings page cannot exist, and the updates row stays
  hidden.
- Change: 3 patches: the panel; the tiles, with the mockup's sidebar order and the
  Appearance mapping (B4); and the updates row and page on `Update1`. Nine of the
  panel's 14 rows bind stock GNOME or Dash to Dock keys. One schema,
  `io.github.sekirokenjii.Apex.Desktop`, holds six keys. The standalone Updates app and
  the Tweaks page are dropped. "Apex Tweaks" opens the panel.
- Answer 1 (§5.3): the Appearance mapping is not needed (B4), and the dock's rows bind
  Apex keys, since Dash to Dock goes (B6).

**B6. The dock: build or adopt.** Medium.
- Evidence: html:290-308, 724-725. Dash to Dock v109 (GPL-2.0-or-later) supports shell
  45 to 51. Fedora's v105 RPM stops at 50. Blur my Shell release 72 and Rounded Window
  Corners Reborn also stop at GNOME 50 on extensions.gnome.org (2026-09-28).
- Impact: the dock is the largest single visible gap on screens 03 to 08.
- Change: vendor v109 by commit. Every row maps to its keys except running indicators,
  which get one Apex key. Styling is Apex CSS; glass comes from apex-shell.
- Review: an owned 1.5K-line dock was rejected. Reopen only if the dock goldens cannot
  pass through CSS and keys, or if Dash to Dock lags a GNOME beta by more than 4 weeks
  (ADR 0014).
- Answers 1 and 26 (§5.3): the dock details in `design/SPEC.md` §8 need Dash to Dock
  code changes, which meets this finding's reopen trigger. ADR 0014 builds Apex's own
  dock on upstream `js/ui/dash.js` inside the rebuilt shell.

**B7. The drawn search shortcuts collide.** Medium.
- Evidence: the mockup opens search with Ctrl+Space or Alt+Space (html:587). Alt+Space
  is mutter's window menu. Ctrl+Space is completion in IDEs and editors. Super+Space
  switches input (override:13-19).
- Impact: as drawn, a developer loses code completion in every IDE, and Alt+Space is
  taken from mutter's window menu.
- Change: owner decision 6. Recommended: a Super tap opens Spotlight. Until Spotlight
  exists (S3a), it opens the stock overview search. One search engine serves every entry
  point.
- Answer 6 (§5.3): Super+Space opens Spotlight. Input switching moves to
  Super+Alt+Space (with Shift for backward), which no GNOME 51 default uses. A Super
  tap still opens the overview.

**B8. Glass costs frame time and battery.** Medium.
- Evidence: every glass surface uses `saturate(130–180%)`. `Shell.BlurEffect` has only
  radius, brightness and mode (`shell-blur-effect.c:95-98`). Background mode "can be
  computationally expensive" (`:42`).
- Impact: live blur on every surface costs battery and frames on a Vega 7 iGPU at
  2880×1800 and 90 Hz.
- Change: owner decision 14. Recommended:
  - static cached glass for the bar, the idle dock and the scrims, with a
    `Clutter.ShaderEffect` for saturation;
  - dynamic blur only for the dock while a window overlaps it, and for popovers while
    open.

  S3a measures this once on the laptop, on battery at 90 Hz. Targets: p99 frame time at
  most 11.1 ms in a Sysprof capture of mutter's frame marks, and an idle cost of at most
  0.3 W against Reduce Transparency. The protocol is in the roadmap. These are
  measurements, not build gates.
- Answer 14 (§5.3): dynamic blur everywhere, with the drawn saturation, through a
  patched `ShellBlurEffect` in the rebuilt shell. Reduce Transparency stays the off
  switch. The targets above become the exit of the glass work (roadmap S2b and S3a).

**B9. Icons.** Medium.
- Evidence: the mockup uses Colloid app icons (`design/mockup/github.md`) and Hugeicons
  glyphs (html:14). The image ships Adwaita only (`gnome.txt:26`). Hugeicons' 1.5-unit
  strokes on a 24-unit grid do not land on device pixels at 18 px.
- Impact: every icon in the dock, grid, overview and Files differs from the mockup, and
  18 px strokes render soft.
- Change: an `Apex` theme from a pinned upstream Colloid commit (apps, places,
  mimetypes, app-ID aliases), inheriting Adwaita. The copies in
  `design/mockup/icons/` carry C2PA provenance manifests and are not used for the
  build. The symbolic glyphs are owner decision 11 (S5). Only the free Hugeicons set is
  MIT.
  A glyph that exists only in Hugeicons Pro stays Adwaita.

**B10. Fonts and sizes.** Medium.
- Evidence: Adwaita Sans is the mockup's Inter with `cv05` frozen and the same axes;
  `ss03` is in GSUB. JetBrains Mono is not shipped. The mockup draws 13.5 px body text
  but labels it "Inter 11" (14.67 px).
- Impact: with "Adwaita Sans 11" every text run is about 1 px taller than drawn, which
  shifts rows and truncation. Terminal text renders in Adwaita Mono.
- Change: a fontconfig `fontfeatures` rule for `ss03`; `jetbrains-mono-fonts`; font
  keys per owner decision 12.

**B11. Boot, lock and login have no implementation path.** Medium.
- Evidence: `plymouth-system-theme` shows the spinner and the ASUS logo
  (`base.txt:36-40`). The lock screen is stock two-stage. The greeter has no design.
  The GRUB menu flashes for 1 s.
- Impact: the first thing seen at every power-on contradicts the design.
- Change:
  - An `apex` two-step Plymouth theme (S1c). One full-screen watermark image carries
    the wordmark and the footer, rendered from os-release at image build. The theme is
    set before the existing dracut run (`Containerfile:400-403`).
  - The shared shell theme styles lock and greeter. `apex-lock` makes the lock
    single-stage, as drawn (S3b).
  - The GRUB menu stays hidden unless the last boot failed. This is a spike in S4,
    where Windows joins the ESP. Esc during the timeout and the firmware boot menu must
    still reach Windows.
- Answers 17 and 26 (§5.3): the recommended handoff. The boot bar's radius is built
  with a script-plugin Plymouth theme (roadmap S1d), with the two-step theme as
  fallback. The lock is single-stage inside the rebuilt shell. The owner will delete
  Windows later; roadmap step W removes the dual-boot parts then. Until then Windows
  starts from the firmware boot menu only; GRUB gets no Windows entry
  (`docs/INSTALL.md:420-423`).

**B12. The app set does not match the dock and grid.** Medium.
- Evidence: no gnome-music, gnome-maps or GTK4 mail client. GNOME Photos is excluded.
  Software is the Bazaar Flatpak. Disks is GTK3 (`gnome.txt:46-74`,

**B13. Most surfaces are styling on stock structure.** Medium.

  (262-288), the launcher (243-260), window chrome (648-653) and Files (24-85).

  - The notification close button is always visible, as drawn. Stock GNOME 51 does the

  - The calendar's week start and the clock format follow the locale.

**B14. The mockup's app-chrome greys differ from libadwaita.** Medium.
- Evidence: dark window `#242428` against `#222226`, dark header bar `#242428` against

**B15. HIG tensions and undesigned surfaces.** Medium.

- Impact: each item is cheap to decide now and expensive after code exists. A

- Change: the owner has already approved the mockup's HIG deviations: the persistent

### 3.3 Build lane and image

**C1. There is no lane for patched GNOME packages, and the only template degrades to
stock.** High.
- Evidence: `packaging/libfprint/build.sh` hard-codes libfprint (`:161-168`,
  `:405-412`). The Containerfile detects it by name (`:156-161`). `apex.txt:12-18` is a
  hand-kept `includepkgs` list. Failure ships stock (`build.sh:30-33`,
  `ARCHITECTURE.md:114-117`).
- Impact: engine patches cannot ship, and copying the degrade policy would make the
  design vanish overnight.
- Change: `packaging/rebuild.sh <pkg>` with `packaging/pkgs/<pkg>/`. It generates
  `includepkgs` and `excludepkgs` and applies patches with fuzz 0. The failure policy is
  per package: hold for gnome-control-center and nautilus, degrade for libfprint
  (ADR 0014). libfprint moves in first, and its RPMs are diffed against today's build.

- Review: the coupling claim was overstated. `gnome-shell.spec:88` requires only
  `mutter >= 51.0`, so a patched shell would run on stock mutter. `[apex]` priority 1

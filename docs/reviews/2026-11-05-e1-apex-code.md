## 4. The typing stall: cause and E2 fix

**Cause.** The first diagnostics pass after the first edit runs
`IdeDiagnosticTool::prepare_run_context()`. It looks up its program (flake8 for Python)
three ways, each on the main thread:

- by path and by name, with `ide_pipeline_contains_program_in_path()`;
- then on the host, with `ide_runtime_contains_program_in_path()`.

Each lookup spawns `which` and blocks on `ide_subprocess_wait_check()`. In the toolbox
that is a `podman exec`, 134–177 ms each; on the host it is a login shell, 61–151 ms
each. That adds up to 0.63 s here and 0.76 s in E0. The runtimes cache both answers, so
it happens once per program and runtime. Builder's log shows
`Failed to locate program "flake8"` at the end of the stall. Installing flake8 would not
help: a found program costs the same lookups.

**E2 fix, proposed (≤ 200 ms stall budget).** Take the lookups off the main thread:

- When the pipeline is ready, prime the runtimes' path caches from a libdex fiber, for
  the programs of the diagnostic tools the project's languages load.
- Make `prepare_run_context()` read the cache only; on a miss it skips that diagnostics
  pass, and the next keystroke finds the answer.

It touches `ide-diagnostic-tool.c` and both runtimes (podman and host), so it is an
upstream patch to propose. `run.sh` gains a stall check: type for 60 s and fail on any
frame over 200 ms.

## 5. One shared `podman exec` per toolbox

**Today.** Every process Builder runs in the toolbox is its own `podman exec`. Its Go
client stays alive as the process's stdio, at about 48 MiB RSS (26 MiB PSS), beside a
`conmon` of about 2.3 MiB. Three servers cost about 140 MiB on the host (E0).

**Design.**

1. Per toolbox, one `podman exec --detach` starts a small bridge inside the toolbox. It
   listens on a socket in `$XDG_RUNTIME_DIR`, which toolbox shares with the host.
2. For each process, Builder sends argv, environment and working directory, and passes
   the stdio fds with `SCM_RIGHTS`. The bridge spawns the process on those fds and
   returns its exit status and signals over the socket.
3. No client copies stdio, so the host keeps one `conmon` per toolbox: about 2 MiB in
   all, under E2's ≤ 20 MiB.

**Shipping.** The bridge ships on the host and runs from `/run/host/usr/libexec/`, since
toolbox mounts the host's root at `/run/host`. It needs the same Fedora or a static
link. In Builder it is a second run handler in the podman runtime, for toolbox
containers only, about 400 lines in all.

**Risk.** If the bridge dies, every server dies with it. The runtime should restart it
once and otherwise fall back to one `podman exec` per process.

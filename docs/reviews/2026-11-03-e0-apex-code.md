# E0: Apex Code, a measured spike (2026-11-03)

Status: measured in a cloud container; laptop numbers come later from the owner. Path in
the repo: `docs/reviews/2026-11-03-e0-apex-code.md`. It answers the E0 item of track E in
the [ROADMAP](../ROADMAP.md) and the questions [ADR 0017](../adr/0017-apex-code-on-builder.md)
left to E0. The numbers here set the E1–E3 budgets proposed in §9. The laptop rerun
replaces them where they differ.

## 1. Summary

- **Builder 50 is the lightest of the measured editors.** With apex-gnome open, its own
  process tree uses 345 MiB RSS idle and 405 MiB at the end of 60 s of typing; VSCodium
  uses 1224 MiB and 1269 MiB. In PSS, which counts shared pages once, the figures are
  258/318 MiB against 592/633 MiB.
- **Cold start:** Builder paints its first window in 1.83 s and is visually settled at
  1.93 s. VSCodium paints a first frame sooner (1.24 s), but its workbench keeps
  repainting until 5.21 s.
- **Input latency is a tie when keys are spaced:** key to painted frame, median 21.6 ms
  for Builder and 21.3 ms for VSCodium (60 keys each, 1 s apart). While typing at
  6.7 keys/s, Builder has one main-loop stall of about 0.76 s, 2.4 s into the run, plus a
  slow first key. VSCodium has none. E1 has to explain the stall and E3 has to remove it.
- **Toolbox runtime works,** with two traps: the project has to be under a path the
  toolbox shares (`$HOME`), otherwise Builder respawns each language server every 5 s
  with no visible error. Each server also costs a `podman exec` client of about 48 MiB RSS.
- **ACP fits as a built-in plugin** (a workspace addin with an `IdePane`), but jsonrpc-glib
  only speaks LSP's `Content-Length` framing, while ACP over stdio uses
  newline-delimited JSON. The plugin needs its own small transport.
- **Zed was not measured.** Running its unsigned upstream tarball was refused by this
  session's permission policy. §2.4 says what is needed to fill its rows.

## 3. Memory (RSS and PSS)

**Method.** The editor is launched from inside gnome-shell (`Gio.SubprocessLauncher`).
The harness then sums `Rss` and `Pss` from `/proc/<pid>/smaps_rollup` over the process
tree: Builder's main process with its children, or every process whose command line is
`/usr/share/codium/codium` (VSCodium's launcher script exits, and its helpers hang off
the main process). A process whose command line names a language server, together with
its subtree, is counted apart. **Idle:** the project and the typing file are open and the
window is maximised; after 30 s settled, 10 samples are taken 1 s apart and the median is
reported. **Typing:** 400 characters of Python-like lines (`total_count = base_value +
offset * 2`, Return at each line end), one key every 150 ms (6.7 keys/s) for 60 s,
through a Clutter virtual keyboard created in the compositor. A sample is taken every 13
keys (30 samples).

| KiB → MiB | Builder | VSCodium |
| --- | --- | --- |
| Idle RSS, median of 10 (min–max) | **345** (345–349) | **1224** (1224–1224) |
| Idle PSS, median | 258 | 592 |
| Typing RSS, median / max of 30 | 405 / 405 | 1256 / 1269 |
| Typing PSS, median / max | 318 / 318 | 620 / 633 |
| Processes in the tree | 3 | 9 |
| Language servers | none (§3.1) | none (§3.1) |

Builder's three processes, idle: `gnome-builder` 315 MiB RSS (247 MiB PSS),
`gnome-builder-flatpak` 16 MiB, `gnome-builder-git` 14 MiB. The flatpak helper runs even
when no Flatpak runtime is used. VSCodium's nine processes: the main process 222 MiB, the
renderer 264 MiB, the GPU process 158 MiB, three Node utility processes (extension host,
file watcher, shared process) of 113–146 MiB, the network service 81 MiB, and two
zygotes of 58 MiB each.

**3.1 No language servers in these runs.** The container's host side has none installed,
because Apex runs them in a toolbox (ADR 0017 §4). VSCodium's built-in language features
for Python are only a grammar, so it starts none either. The language-server cost is
measured with the toolbox in §6.

**Limits.** RSS double-counts pages that processes share, which flatters a
single-process editor; PSS is the fairer comparison and is given too. Software rendering
puts textures in process memory that a GPU driver would partly keep elsewhere, so both
editors should use less on the laptop, VSCodium's GPU process most. VSCodium runs with
`--no-sandbox`, because Chromium's sandbox will not run as root. That changes the
process model only slightly (the zygotes stay).

## 4. Cold start

**Method.** t0 is stamped inside gnome-shell just before the spawn. The probe connects to
`window-created` for the first normal window, then to that `MetaWindowActor`'s
`first-frame` signal, then takes the next stage `after-paint` (the frame that contains
the window). **Settled** is the window's last damage before 5 s with no damage (40 s
cap): a stand-in for "visually complete". Cold runs drop the page cache first (`sync;
echo 3 > /proc/sys/vm/drop_caches`); warm runs do not. A discarded first run creates the
config directories. Each editor quits with SIGTERM to its main process between runs. The
command is `gnome-builder -p <project>` or `codium <project>`.

Milliseconds after spawn. Three runs each; the median is in bold.

| | Builder: window created | Builder: first frame painted | Builder: settled | VSCodium: window created | VSCodium: first frame painted | VSCodium: settled |
| --- | --- | --- | --- | --- | --- | --- |
| Cold 1 | 1215 | 1844 | 1927 | 1054 | 1239 | 5208 |
| Cold 2 | 1149 | 1775 | 1883 | 1063 | 1263 | 5219 |
| Cold 3 | 1187 | 1826 | 1928 | 1001 | 1187 | 5137 |
| **Cold median** | **1187** | **1826** | **1927** | **1054** | **1239** | **5208** |
| Warm 1 | 933 | 1578 | 1678 | 782 | 942 | 4913 |
| Warm 2 | 1003 | 1533 | 1655 | 688 | 871 | 4804 |
| Warm 3 | 988 | 1735 | 1888 | 722 | 873 | 4815 |
| **Warm median** | **988** | **1578** | **1678** | **722** | **873** | **4815** |

**Reading.** Builder spends about 0.6 s between mapping its window and painting the first
frame. Its log shows GTK 4.24 trying Vulkan, failing ("Failed to enumerate drm devices"),
and falling back to GL on llvmpipe, so a part of that gap belongs to this container. The
laptop rerun has to say how much. VSCodium paints an early skeleton frame and then fills
the workbench for about 4 s.

**Limits.** No GPU, page cache dropped through a VM's virtio disk, and a 4-vCPU guest.
The run-to-run spread is 3–13 %. Three runs are what the brief asked for; they are not
enough for a confidence interval.

## 5. Input latency

**Method, and how it compares with mutter's frame timings.** The measurement runs inside
the compositor, on its monotonic clock (µs). For each key: stamp t0, inject press and
release through a Clutter virtual keyboard on the default seat, watch the focused
window's `MetaWindowActor::damaged` for the first damage after t0, then stamp the next
stage `after-paint`: the composited frame that holds the change. The stage's `presented`
signal never fired on the headless virtual monitor, so `after-paint` stands in for
presentation. On real hardware, presentation follows `after-paint` by up to one refresh
plus scanout; the laptop rerun should use `presented` or mutter's frame-timing debug
output. Two runs:

- **Spaced:** 60 keys, 1.0 s apart, after the 60 s typing run. Each frame belongs to
  exactly one key. This is the headline number.
- **While typing:** the 400 keys of §3, 150 ms apart. When a frame takes longer than
  150 ms, a later key's damage can be credited to the stall, so the tail shows stalls
  but over-counts them.

| ms | Builder, spaced | VSCodium, spaced | Builder, typing | VSCodium, typing |
| --- | --- | --- | --- | --- |
| n | 60 | 60 | 398 | 398 |
| Median (95 % bootstrap CI) | **21.6** (20.6–24.0) | **21.3** (20.8–23.0) | 16.8 (15.6–18.0) | 21.8 (21.4–22.4) |
| p95 | 30.2 | 27.5 | 35.1 | 32.2 |
| p99 | 30.5 | 32.5 | 159.3 | 39.2 |
| Max | 30.8 | 36.0 | 758.9 | 53.9 |
| Keys > 100 ms | 0 | 0 | 5 | 0 |
| Key → client damage, median | 9.7 | 20.3 | 14.8 | 20.4 |
| Damage → painted, median | 13.0 | 0.9 | n/a | n/a |

The typing columns leave out the first two keys of each run. In both editors the very
first key landed while focus was settling (Builder 314 ms; VSCodium 63 ms).

**Error bars.** Each sample is quantised by the 60 Hz frame clock (16.7 ms), so a
single key has an error of about ±8 ms. The bootstrap intervals above are for the
medians. The clock resolution is 1 µs, and D-Bus delay does not enter, because t0 is
stamped in the compositor right before the injection.

**Reading.** Builder commits its new buffer sooner (9.7 ms against 20.3 ms), but waits
for the compositor's next tick (13 ms). Chromium times its commit to the frame callback
and lands about 1 ms before the paint. The totals come out the same. The real defect is
Builder's stall: one blocked main loop of about 0.76 s, 2.4 s into typing. In it, five
queued keys painted at 759, 608, 459, 310 and 159 ms. It did not recur in the next 57 s
or in the spaced run. The likely suspects are the first-edit work (spell checking, git
change tracking, ctags, word completion) and the Python language plugins starting without
a server; the verbose log has to tell which.

**Limits.** "First damage of the window" can be any repaint the key caused, not only the
glyph. With the cursor blink off, screenshots show the text typed correctly in both
editors. Software rendering slows Chromium's raster more than GTK's, so the tie may break
either way on the laptop.

## 6. Toolbox runtime

**Method.** `toolbox create` from `fedora-toolbox:45`. Inside it: `dnf install
rust-analyzer cargo rust python3-lsp-server nodejs npm` and `npm install -g
typescript-language-server@4 typescript@5`. The project gets a `.buildconfig` whose
default configuration selects `runtime=podman:<container id>`. Builder opens a `.py`
file with an undefined name, a `.ts` file with a type error, and a small cargo crate
(`tests/e0rs`) with a type error, 45 s apart. It then settles 30 s and takes 5 samples.

**Does it work.** Yes, for all three servers. Builder 50 starts a server in the build
pipeline's runtime first, then on the host, then in its own environment
(`ide_lsp_service_create_launcher`). With the toolbox selected, all three ran inside it:
each server's `/proc/<pid>/root/etc/os-release` reads "Fedora Linux 45 (Toolbx
Container Image)". The TypeScript error showed inline (gutter mark and underline).
pylsp and rust-analyzer answered document symbols (the status bar showed `os` and
`main`). pylsp showed no diagnostic, because Fedora's `python3-lsp-server` comes without
pyflakes. rust-analyzer's type-mismatch diagnostic comes from `cargo check` on save, which
the run did not do.

**What breaks.**

1. **A project outside the toolbox's shared paths fails silently.** Builder runs
   `podman exec --workdir=<project>`. For a project in `/work`, which a toolbox does not
   share, crun fails with exit 127, and Builder respawns the server every 5 s without
   end. The status bar keeps showing `0 0`. Projects under `$HOME` work. E1 has to detect
   this (check the workdir, back off, and show an error).
2. **The runtime reads podman's storage itself, and gets the system path wrong.**
   `get_storage_directory()` in `src/plugins/podman/gbp-podman-runtime.c` builds the
   global path with `g_build_filename ("etc", "containers", "storage.conf", NULL)`: a
   relative path missing its leading `/`. It never reads `/etc/containers/storage.conf`
   and falls back to `~/.local/share/containers/storage`. For rootless podman, the Apex
   default, that fallback is right. Otherwise Builder logs "Cannot read overlay folder"
   and its file translation is off. A one-line upstream fix.
3. **Root and rootful podman are second-class.** Toolbox as root needed `SHELL` set, and
   nested podman needed `pids_limit=0` on this host. These are container artefacts, but
   E1's image test has to run toolbox as a normal user on cgroup v2.
4. **The pipeline restarts the language servers several times at startup**
   ("Pipeline changed, requesting LSP service … restart" 8 times while the project
   loaded). Harmless here, but it delays the first diagnostics.

**What it costs, in MiB, median of 5 samples once settled.**

| | RSS | PSS |
| --- | --- | --- |
| Builder process tree, project open, no file (before) | 293 | 205 |
| Builder process tree, three servers running | 512 | 360 |
| … of which the 3 `podman exec` clients | 140 | 76 |
| … of which `gnome-builder` itself | 342 | 272 |
| Language servers, total | 581 | 426 |
| … `tsserver` ×2 and the typings installer (TypeScript) | 400 | 293 |
| … `typescript-language-server` (Node) | 57 | 26 |
| … `pylsp` and its jedi subprocess | 72 | 58 |
| … `rust-analyzer` (one-file crate) | 53 | 49 |
| Toolbox glue outside Builder: `conmon` ×4, `toolbox init-container` | 23 | n/a |

The runtime's own overhead is mostly the Go `podman exec` client that each server keeps
alive: about 48 MiB RSS (26 MiB PSS) per server. A single exec'd launcher in the toolbox
that multiplexes the servers' stdio would cut that to one client. That is E1 work.
rust-analyzer's number is for a one-file crate; a real workspace will be larger.

## 8. ACP fit

**Short answer: it fits as a plugin, with two new pieces: a newline-delimited JSON-RPC
transport and a panel UI. Neither needs changes to libide.**

**What Builder 50 offers.**

- **Plugins.** libpeas 2. The Fedora build ships its plugins built in (`Builtin=true`,
  `Embedded=…` in each `.plugin`), so an Apex plugin lives in the series under
  `src/plugins/acp/`, like the terminal and todo plugins. The GJS loader is also turned
  on when the `Ide-1` typelibs load (they ship in
  `/usr/lib64/gnome-builder/girepository-1.0`), and `~/.local/share/gnome-builder/plugins`
  is searched. A GJS prototype can therefore come before the C plugin, without
  rebuilding.
- **UI hooks.** `IdeWorkspaceAddin` adds an `IdePane` (libpanel) to an edge; the terminal
  plugin (`gbp-terminal-workspace-addin.c`) is the model. `IdeEditorPageAddin` gives
  access to the open buffer and view, for showing an agent's proposed edit inline.
- **Process spawning in the right place.** `IdeRunContext` with
  `ide_pipeline_prepare_run_context()` runs a program in the configured runtime, which is
  the toolbox on Apex (§6). That is the same path the language servers take.
- **Async.** libdex futures and `IdeTask`; jsonrpc-glib 3.44.2 for JSON-RPC.

**What does not fit as is.**

1. **Framing.** ACP over stdio sends one JSON-RPC message per line, with no embedded
   newlines. jsonrpc-glib's `JsonrpcInputStream` expects a `Content-Length:` header and
   `JsonrpcOutputStream` writes one (`jsonrpc-input-stream.c:194`,
   `jsonrpc-output-stream.c:188`). `JsonrpcClient` builds those streams itself, so they
   cannot be swapped. The plugin needs a transport of about 300 lines: a
   `GDataInputStream` reading lines plus json-glib, with request ids, pending calls and
   cancellation. Proposing a newline mode to jsonrpc-glib upstream would be the cleaner
   fix later.
2. **The client side of ACP is larger than LSP's.** The agent calls the editor, so the
   plugin implements:
   - `fs/read_text_file` and `fs/write_text_file`, through `IdeBufferManager`, so the
     agent sees unsaved buffers and writes go through undo;
   - `session/request_permission`, an inline approval row in the panel;
   - `terminal/create`, `terminal/output`, `terminal/wait_for_exit`, `terminal/kill` and
     `terminal/release`, through `IdeRunContext` in the toolbox, mirrored to a terminal
     page;
   - rendering of `session/update` notifications (message chunks, tool calls, plans,
     diffs).

   The calls it makes are `initialize`, `session/new` (cwd and MCP servers),
   `session/prompt`, `session/cancel` and, when the agent offers it, `session/load`.
3. **No widgets for the content.** Builder renders Markdown only through WebKit
   (`markdown-preview`), which is too heavy for a chat stream. It has no diff view. E3
   needs a lightweight Markdown-to-`GtkTextView` renderer and a diff widget. The diff
   widget doubles as the multibuffer view, so it is worth building once for both.
4. **Agents live in the toolbox.** ACP agents such as a Claude Code adapter are Node
   programs. They run in the toolbox like the language servers, and paths match because
   the toolbox shares `$HOME`. Plain podman runtimes need `ide_runtime_translate_file()`
   on every path the agent sends.

**Cost.** The panel's own memory should stay under 30 MiB beside an idle Builder. The
agent process is counted apart, like a language server. Latency has to stay off the main
loop: parse on a libdex worker and hand finished updates to GTK in batches, one per
frame, so a streaming answer cannot cause the stall seen in §5.

## 10. Limits of this spike

- No GPU: every client renders in software. Start-up and latency on the laptop will
  differ, VSCodium's probably the most.
- A 4-vCPU cloud VM, a 60 Hz virtual monitor, `after-paint` instead of `presented`.
- Root everywhere: toolbox and podman ran rootful, and VSCodium ran without its sandbox.
- Three cold runs per editor, as briefed. One typing run and one spaced run per editor.
- Zed not measured (§2.4).

## Appendix A. Harness

Run inside a `fedora:45` container with systemd and a 2 GiB `/dev/shm`. Each script is
given whole. In the cloud run, the image also trusted a proxy CA and installed with the
`fedora-cisco-openh264` repository disabled; both are left out below.

### A.1 Image

```dockerfile
FROM registry.fedoraproject.org/fedora:45
RUN dnf -y install --setopt=install_weak_deps=False gnome-builder gnome-shell mutter dbus-daemon dbus-tools \
    at-spi2-core python3-gobject python3-dbus python3-pyatspi mesa-dri-drivers mesa-vulkan-drivers vulkan-loader \
    procps-ng psmisc git podman toolbox fuse-overlayfs adwaita-mono-fonts adwaita-sans-fonts \
    xorg-x11-server-Xwayland gsettings-desktop-schemas jq tar gzip findutils which systemd && dnf clean all
RUN printf '[vscodium]\nname=vscodium\nbaseurl=https://download.vscodium.com/rpms/\nenabled=1\ngpgcheck=1\nrepo_gpgcheck=1\ngpgkey=https://gitlab.com/paulcarroty/vscodium-deb-rpm-repo/raw/master/pub.gpg\nmetadata_expire=1h\n' > /etc/yum.repos.d/vscodium.repo && \
    dnf -y install codium && dnf clean all && \
    systemctl mask systemd-firstboot.service systemd-homed.service systemd-networkd.service systemd-resolved.service getty@tty1.service
```

Started as `docker run -d --privileged --cgroupns=private --shm-size=2g -v $PWD/e0:/e0 -v $PWD/out:/out -v <apex-gnome>:/src/apex-gnome:ro e0 /e0/init.sh`. ```python
#!/usr/bin/python3
# E0 driver: runs inside the e0 container's headless GNOME session.
import sys, os, json, time, re, subprocess, statistics
sys.path.insert(0, '/e0'); from ev import ev
def load(): return ev(open('/e0/probe.js').read())
LSP = re.compile(r'rust-analyzer|typescript-language-server|tsserver|pylsp|pyright|basedpyright|jedi-language-server|ruff|clangd|bash-language-server|vala-language-server|gopls|blueprint-compiler|jsonServerMain|cssServerMain|htmlServerMain|markdown-language-features|serverMain')
def children(pid):
    out = []
    for p in os.listdir('/proc'):
        if p.isdigit():
            try:
                pp = int(open(f'/proc/{p}/stat').read().rsplit(')', 1)[1].split()[1])
            except Exception: continue
            if pp == pid: out.append(int(p))
    return out
def tree(pid):
    res, stack = [], [pid]
    while stack:
        p = stack.pop(); res.append(p); stack.extend(children(p))
    return res
def mem(pid):
    d = {'rss': 0, 'pss': 0}
    try:
        for l in open(f'/proc/{pid}/smaps_rollup'):
            if l.startswith('Rss:'): d['rss'] = int(l.split()[1])
            elif l.startswith('Pss:'): d['pss'] = int(l.split()[1])
        d['cmd'] = open(f'/proc/{pid}/cmdline').read().replace('\0', ' ').strip()[:160]
    except Exception: return None
    return d
def sample(roots, extra_match=None):
    """Sum RSS/PSS (KiB) for editor vs language servers. A process is an LSP if its cmdline matches; its subtree too."""
    ed, ls, procs = {'rss': 0, 'pss': 0, 'n': 0}, {'rss': 0, 'pss': 0, 'n': 0}, []
    seen = set()
    pids = []
    for r in roots: pids += tree(r)
    if extra_match:
        for p in os.listdir('/proc'):
            if p.isdigit():
                try: c = open(f'/proc/{p}/cmdline').read()
                except Exception: continue
                if re.search(extra_match, c): pids += tree(int(p))
    lsp_roots = set()
    for p in pids:
        m = mem(p)
        if not m or p in seen: continue
        seen.add(p)
        is_lsp = bool(LSP.search(m['cmd']))
        m['pid'] = p; m['lsp'] = is_lsp; procs.append(m)
    # descendants of an LSP count as LSP
    lsp_pids = set()
    for m in procs:
        if m['lsp']: lsp_pids.update(tree(m['pid']))
    for m in procs:
        m['lsp'] = m['pid'] in lsp_pids
        b = ls if m['lsp'] else ed
        b['rss'] += m['rss']; b['pss'] += m['pss']; b['n'] += 1
    return {'editor': ed, 'lsp': ls, 'procs': procs}

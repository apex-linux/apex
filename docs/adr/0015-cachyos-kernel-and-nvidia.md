# ADR 0015: CachyOS kernel and NVIDIA open modules, built as one pair

Status: accepted (2026-09-28). It records the owner's answer to decision 22
(`docs/reviews/2026-09-28-review.md` §5.3). It supersedes ADR 0005, and amends ADR 0012
(Secure Boot keys and third-party sources) and ADR 0004 (where a kernel quirk is
carried).

## Context

The owner's answer:

- The kernel is CachyOS's GCC build, not the Clang/LTO build.
- The NVIDIA kernel modules are built for exactly the image's kernel. They are
  precompiled in the image and never built on the laptop.
- The RTX 3050 Mobile (GA107M, `10de:25a2`) is used, not left off.
- Secure Boot is off on the laptop today (`mokutil --sb-state`, 2026-09-28).

## Decision

### 1. The kernel

- The image boots `kernel-cachyos`, the GCC build (BORE, HZ 1000, x86-64-v3). The
  `-lto`, `-rt`, `-server` and `-lts` variants are not used.
- Apex rebuilds it from the COPR's signed SRPM in the builder VM
  (`packaging/pkgs/kernel/`, ARCHITECTURE §4.2). COPR binaries are never installed.
  The rebuild lets the kernel and the NVIDIA modules share one signing key (§3), lets
  Apex carry a hardware patch (§8), and keeps COPR's build hosts out of the trust chain.
- `kernel-spec.patch` (fuzz 0) changes only build mechanics:
  - `Release: cachyos1.apex<N>%{?dist}`, so `uname -r` is
    `7.2.8-cachyos1.apexN.fc45.x86_64` and no COPR build can satisfy
    `kernel-uname-r`;
  - `_disable_source_fetch 1`;
  - in `%prep`, before `olddefconfig`, `scripts/config --set-str MODULE_SIG_KEY` names
    the pair's per-build key on a tmpfs (§3);
  - patches from `series`, if any (§8);
  - `%posttrans` and `%preun` reduced to `depmod`: no `kernel-install`, no dracut, no
    copy into `/boot`;
  - `CC="ccache gcc"`.
- CachyOS's configuration is used as shipped. `MODULE_SIG_KEY` is the only change. A
  configuration change between two bumps, other than new symbols, holds the bump for
  the owner's review, because the config comes from an unpinned URL.
- The image carries exactly one kernel. The Fedora repositories get `excludepkgs` for
  exactly `kernel`, `kernel-core`, `kernel-modules`, `kernel-modules-core`,
  `kernel-modules-extra`, `kernel-devel`, `kernel-devel-matched`, `kernel-uki-virt` and
  `kernel-uki-virt-addons`. The pattern is not `kernel*`, so `kernel-headers` and
  `kernel-tools` stay Fedora's.
- Kernel arguments:
  - `module.sig_enforce=1`: every module must carry a signature the kernel trusts,
    with Secure Boot off too (§3);
  - `zswap.enabled=0`: the CachyOS config turns zswap on, and Apex uses Fedora's zram
    (`image/packages/base.txt:41`);
  - `module_blacklist=nouveau,nova_core` replaces `modprobe.blacklist=` and
    `rd.driver.blacklist=` (`image/system_files/usr/lib/bootc/kargs.d/10-apex.toml:39-40`).
- CachyOS defaults that differ from Fedora stay unless a measurement says otherwise
  (K3): full preemption (`preempt=lazy` restores Fedora's), BORE (`kernel.sched_bore=0`
  turns it off at runtime), THP always, split-lock mitigation off. RCU lazy is built but
  off; `rcutree.enable_rcu_lazy=1 rcu_nocbs=all`, ADR 0005's power idea, is measured
  without a rebuild. amd-pstate stays in active mode with CachyOS's `epp_boost` off.

### 2. The NVIDIA modules, built for exactly that kernel

- The open kernel modules only. The proprietary flavour is not built.
- Source: negativo17's `nvidia-kmod` SRPM, pinned by sha256 and checked against the
  negativo17 key.
- Built in the same job as the kernel, in the same fresh `fedora:45` container, against
  the `kernel-cachyos-devel` that job just built. `rpmbuild --define 'kernels <uname-r>'`
  builds through kmodtool, the same path akmods uses. kmodtool takes `--for-kernels`
  before the spec's `buildforkernels akmod`, so no akmod package is made and the spec
  needs no edit for this. It produces `kmod-nvidia-<uname-r>` with
  `Requires: kernel-uname-r = <uname-r>` (kmodtool's template for a kernel with
  `/usr/src/kernels/<uname-r>`).
- The kernel and the kmod are built with the same Fedora GCC. The job fails when the
  GCC major in the kernel's `CONFIG_CC_VERSION_TEXT` differs from the container's.
- akmods, akmod-nvidia, dkms, dkms-nvidia, kmodtool and kernel-devel are excluded from
  the image. Nothing compiles modules on the laptop.
- negativo17 follows NVIDIA's newest branch: 615, a new feature branch, today. It does
  not publish the 595 production branch. Apex accepts this and guards driver bumps with
  a soak and a laptop run (§4).

### 3. Module signing: one key per build; the Apex MOK only for Secure Boot

- **A per-build key.** The pair job generates an ECDSA P-384 key and certificate on a
  tmpfs, with the CN `Apex kernel <uname-r> <content key>`. The kernel build embeds the
  certificate in its builtin keyring and signs every in-tree module with it
  (`MODULE_SIG_ALL`, SHA-512, then zstd). The kmod build signs every NVIDIA `.ko` with
  it through kmodtool, after stripping and before xz compression
  (`_kmodtool_signmodules_privkey`, `_kmodtool_signmodules_pubkey`); kmodtool's
  `brp-kmodsign` always uses SHA-256, which the kernel verifies (`CRYPTO_SHA256=y`).
  Then the tmpfs is shredded. Only the certificate leaves the job, to the store.
- kmodtool skips signing without a word when the key path is missing, so the lane gate,
  not kmodtool, proves that every module carries this build's signature.
- **Effect with Secure Boot off.** `module.sig_enforce=1` holds: every module on the
  image is signed by the one key its kernel trusts. Nothing is enrolled, and no module
  signing key outlives a build. The owner's answer 21 (one cosign key and one RPM key)
  stays as it is.
- **The cost.** The key cannot outlive the job, so the pair is the unit of build. A
  driver-only bump rebuilds the kernel too, warm (20–45 min), about once a month. Any
  future out-of-tree module must join the pair job.
- **Effect with Secure Boot on.** Module trust stays in the builtin keyring, so it does
  not depend on `.machine` or `.platform`, where upstream and Fedora differ.
  `mokutil --trust-mok` is not needed.
- **The Apex MOK** is a third key and exists only for Secure Boot (§7). It signs
  `vmlinuz` and nothing else. The owner decides it when turning Secure Boot on
  (roadmap step W3), under ADR 0012 as amended here:
  - an RSA-2048 self-signed X.509 certificate with keyUsage `digitalSignature` and
    extended key usage `codeSigning`;
  - generated offline; the private key lives in the builder VM next to the cosign and
    RPM keys, with an offline backup; the public DER is committed as
    `packaging/keys/apex-sb.der` and shipped as `/usr/share/apex/keys/apex-sb.der`;
  - it reaches only an isolated signing step that receives `kernel-cachyos-core` and
    nothing else;
  - rotation: enrol the new key, sign with it, and remove the old one from MokList one
    image later; revocation: `mokutil --mokx`.

### 4. The pair, the hold and the latency limit

- **The pair is the unit.** `packaging/rpms.lock` names one kernel NVR K, one NVIDIA
  driver set D (negativo17 NEVRs with sha256) and `kmod-nvidia-K` built from D.
  `manifest.json` records K, D, the kmod NEVR, the GSP firmware version and the
  fingerprint of the pair's module certificate.
- **The depsolve enforces it.** The kmod requires `kernel-uname-r = K`, and
  `nvidia-kmod-common` requires `nvidia-kmod` of D's version. A kernel never ships with
  a kmod built for another kernel, and the kmod never ships with other firmware or
  userspace.
- **One side moves per published image.** When both have updates, the kernel goes
  first, so a regression points at one side. A driver bump still rebuilds the kernel
  from the same SRPM, so the kernel's source does not change with it.
- **Polling.** A builder timer, every 4 hours on AC, asks the COPR API for the newest
  succeeded fedora-45 build and reads negativo17's repodata. A daily poll would have
  pushed the 48 h and 53 h builds of the sample past 72 h once the build and G4 are
  added.
- **Mirroring.** Every SRPM and every negativo17 binary is stored at first sight.
  COPR keeps 5 builds and negativo17 the last two builds of each package, so a hold or
  a rebuild of an older pair works only from the mirror.

| Input | Normal path | Hold | Limit | At the limit |
|---|---|---|---|---|
| A kernel point release on the running line (7.2.x) | Automatic. It publishes when the lane gates, G1, G2 and G4 pass. | Any failure, or no COPR build yet: `rpms.lock` keeps K, and the image label says `held=kernel-cachyos`. | 72 h from the kernel.org release. Every stable release carries CVE fixes, so each counts as a security update (decision 18). | The owner chooses: wait, or publish the break-glass image (below). Never automatic. |
| The kmod for a new kernel K' | Built in the same job | K stays with its kmod, and every other update flows. The label says `held=kernel-cachyos (nvidia)`. | 72 h for a point release; 14 days for a new line | The owner may publish K' with `degraded=nvidia`: the NVIDIA set is left out, and the dGPU stays unbound in D3cold. `just publish` refuses a grown degraded set without the owner's override. |
| A new kernel line (7.2 to 7.3) | Waits for the owner: the bump report, a config review, and the laptop rows | The running line stays. | 14 days from the COPR's first build of the line. The old line's end of life upstream is the hard stop. | As in the first two rows |
| A new NVIDIA release D' | 7 days in negativo17 without a replacement; the matching Flathub `GL.nvidia` extension exists; the owner runs ACCEPTANCE §4 on the staged deployment | D stays | none: D keeps working | n/a |
| A pair that passes the gates but regresses on the laptop | n/a | `packaging/hold.txt` pins the last good pair by content key | The 72 h rule of the running line still applies | As in the first row |

- A driver release named in an NVIDIA security bulletin skips the 7-day soak. The
  owner's laptop run stays.
- **Latency.** From a kernel.org release, Apex adds the COPR's time (13–103 h for the
  releases it built, median about 38 h), up to 4 h of polling and 1–2 h of building and
  checking. The expected total is comparable to Fedora's 35–180 h. A release the COPR
  skips starts the clock too, and only the next COPR build stops it. In the sample, two
  of eight point releases passed 72 h this way (7.2.4, about 138 h, because the COPR
  skipped it; 7.2.6, 98 h), both in September, so the owner can expect a
  wait-or-break-glass choice once or twice a month.
- If such holds prove frequent, the lane can build from the signed CachyOS tag and the
  COPR spec at its git commit, with the config and the BORE patch fetched at pinned
  commits, without waiting for the COPR SRPM. The tag-to-COPR lag is measured during S4
  before this is built.
- **Embargoed issues.** Whether CachyOS receives linux-distros pre-disclosure is
  unverified. Fedora does, through Red Hat. For a public, severe kernel issue that
  Fedora has fixed and CachyOS has not, the break-glass image is the answer.
- **Break-glass image.** `just image KERNEL=fedora` builds the same image with Fedora's
  signed kernel and the NVIDIA half built for it, without `module.sig_enforce=1`. With
  Secure Boot off, its NVIDIA modules load with the unsigned-module taint. With Secure
  Boot on, Fedora's kernel enforces module signatures and does not trust the per-build
  key, so the break-glass image runs without NVIDIA. It is built once in S1c to prove
  it boots, and never published automatically, because decision 22 names CachyOS.
- **On the laptop the pair is atomic.** Each deployment's `/usr` carries its own
  kernel, modules and NVIDIA set. The counted boot (ADR 0009) rolls back a kernel that
  panics, and `bootc rollback` returns to the previous pair.

### 5. NVIDIA userspace, Wayland only

- Installed: `kmod-nvidia-<K>`, built by Apex from negativo17's SRPM (§2). From
  negativo17's binaries: `nvidia-kmod-common` (with the GSP firmware),
  `nvidia-modprobe`, `nvidia-driver`, `nvidia-driver-libs`, `nvidia-driver-common`
  (NVML and `nvidia-powerd`), `nvidia-driver-cuda` and `-cuda-libs` (`nvidia-smi`,
  CUDA, NVENC and NVDEC), `nvidia-persistenced` (a dependency only, kept disabled) and
  `nvidia-driver-selinux`. From Fedora: `egl-gbm`, `egl-wayland2`, `egl-x11`,
  `libvdpau`, `ocl-icd` and `opencl-filesystem`.
- Not shipped, each guarded in `image/packages/exclude.txt`: `xorg-x11-nvidia` (the
  Xorg driver), `nvidia-settings` (GTK3), `nvidia-xconfig`, `nvidia-libXNVCtrl`,
  `libnvidia-fbc`, `libnvidia-fmdrv`, `libnvidia-imex`, every i686 package.
- The GLX and EGL-X11 client libraries stay. Xwayland clients use them, and they are
  not X server parts. The legacy gate also fails on any file under
  `/usr/lib64/xorg/modules/drivers/`. The allowlist gains no entry.
- The binaries are mirrored into a local repository, `[apex-nvidia]`, with
  `gpgcheck=1` against the pinned negativo17 key and `includepkgs` set to exactly
  `image/packages/nvidia.txt`. They keep negativo17's signature, and
  `packaging/pkgs/kernel/nvidia.env` pins their NEVRs and sha256. The compose never
  contacts negativo17.org. The key fingerprint above was fetched over HTTPS; it is
  checked against a second source before it is pinned.
- `nvidia-kmod-common`'s `%post` runs `nvidia-boot-update post`. Without
  `/run/ostree-booted` it edits `/etc/default/grub` and runs `grub2-mkconfig`, or edits
  `/etc/kernel/cmdline`, whichever exists in the compose root. K1 records what it does
  there; G1 asserts that both files are untouched and `/boot` is empty. The nouveau
  blacklist lives in `kargs.d` instead.

### 6. Hybrid graphics and power

- The AMD Vega 7 is `boot_vga`. It drives the panel and HDMI and runs gnome-shell,
  including all glass. Compositing never moves to the dGPU.
- A udev rule tags the NVIDIA DRM card `mutter-device-ignore` (mutter 51
  `src/backends/meta-udev.c`). It is generated from `drives_displays = false` in
  `hardware/m7400qc/profile.toml:81-86`. mutter and the greeter then never open the
  NVIDIA KMS node, so a monitor change does not probe the dGPU. No rule tags NVIDIA as
  the preferred primary GPU. This is proactive, not yet measured on GNOME 51; the
  offload and hotplug rows below prove it.
- Apps run on the dGPU on request, through switcheroo-control's environment:
  - "Launch using Discrete Graphics Card" in the dock and app menus;
  - desktop entries with `PrefersNonDefaultGPU`;
  - `switcherooctl launch` on the command line.
- **Runtime power (RTD3).** `/usr/lib/modprobe.d/apex-nvidia.conf` sets
  `options nvidia NVreg_DynamicPowerManagement=0x02` (fine-grained). The driver's
  default of 3 resolves to 2 on this notebook; the explicit value removes the
  dependence on notebook detection.
- `61-apex-dgpu.rules` replaces `61-apex-dgpu-pm.rules:14-15`. It sets
  `power/control=auto` on `add` and `bind` for every NVIDIA display or audio function
  (classes 0x030000, 0x030200 and 0x040300), so the device also reaches D3cold unbound.
  negativo17's own rule sets `on` at unbind. `apex-dgpu.conf` is deleted.
- `nvidia-persistenced` is disabled in `80-apex.preset`: UVM persistence mode keeps the
  GPU awake ([README ch. 21](https://download.nvidia.com/XFree86/Linux-x86_64/615.71.09/README/dynamicpowermanagement.html)).
- **System sleep (s2idle).** Kernel suspend notifiers, the driver default with the open
  modules. No `nvidia-suspend` or `nvidia-resume` units. negativo17's `nvidia.conf`
  stays as shipped: `NVreg_EnableS0ixPowerManagement=1`,
  `NVreg_PreserveVideoMemoryAllocations=1`, `NVreg_TemporaryFilePath=/var/tmp`. The S0
  runs on Ubuntu compare S0ix handling off and on first. They do not exercise the
  notifiers: Ubuntu's 595.91.07 reads `UseKernelSuspendNotifiers: 0` in
  `/proc/driver/nvidia/params` and suspends through its enabled `nvidia-suspend`,
  `nvidia-resume` and `nvidia-hibernate` units (2026-09-28). The notifier path is first
  measured in K3.
- **Dynamic Boost.** `nvidia-powerd` is on, because this board supports it. It stays on
  only if the laptop run shows no idle cost and no cap on `scaling_max_freq` at idle.
- Fallbacks, only if a row fails: a `power/control` toggle after resume, for a GPU that
  stays in D0; notifiers off with NVIDIA's suspend units, for a hang at suspend
  (negativo17 issue 196).
- **Initramfs.** No NVIDIA modules or firmware. `amdgpu` stays early for Plymouth.
- **Flatpak.** `apex-flatpak-update` installs the Flathub extension that matches
  `/sys/module/nvidia/version`, with the dots turned into dashes
  (`org.freedesktop.Platform.GL.nvidia-615-71-09` for 615.71.09), and removes stale
  versions after a good boot
  ([flatpak#3907](https://github.com/flatpak/flatpak/issues/3907), open since
  2020-10-14, checked 2026-09-28).
- The rewritten ACCEPTANCE §4 is the proof: at least 95 % runtime-suspended over
  10 minutes idle, `D3cold` with VRAM off, offload through switcheroo and back to
  `D3cold` within 30 s, `D3cold` within 60 s after an HDMI hotplug, and `D3cold` before
  and after s2idle.

### 7. Secure Boot: when and how

- **Now:** off. There is nothing to enrol. Module integrity comes from the per-build key
  in each kernel's builtin keyring and `module.sig_enforce=1` (§3).
- **When:** after the owner deletes Windows (roadmap step W3), optional and
  owner-triggered. While Windows shares the ESP, bootloader updates stay off, and a
  Windows Update SBAT revocation can then stop the old shim or GRUB from booting with
  Secure Boot on (`80-apex.preset:42-43`). Turning Secure Boot on also changes PCR 7,
  so BitLocker would ask for its recovery key if Windows had turned it on. On
  2026-09-28 the Windows volume is not encrypted (`lsblk` shows `nvme0n1p3` as `ntfs`).
- **How:**
  1. The owner decides the third key, and the Apex MOK is generated (§3).
  2. The lane starts signing `vmlinuz`: the isolated step receives only
     `kernel-cachyos-core`, runs `sbsign`, repacks with `rpmrebuild` and signs the RPM.
     G1 runs `sbverify --cert` on the image's `vmlinuz`.
  3. `kargs.d` gains `lockdown=integrity`. CachyOS lacks Fedora's lockdown-on-Secure-Boot
     patch, and its `CONFIG_LSM` includes `lockdown`. Lockdown also turns hibernation
     off, which Apex does not use.
  4. Publish until both the booted and the rollback deployment carry a signed kernel.
  5. `sudo mokutil --import /usr/share/apex/keys/apex-sb.der`, reboot, and enrol the key
     in MokManager at the console.
  6. Turn Secure Boot on in the firmware setup.
  7. Check: `mokutil --sb-state` says enabled, `/sys/kernel/security/lockdown` shows
     `[integrity]`, `nvidia` loads, and `amd-s2idle test` still runs under lockdown.
- With Secure Boot on, `IMA_ARCH_POLICY` also enforces module and kexec signatures,
  which the per-build key already satisfies.
- shim and GRUB stay Fedora-signed. The CachyOS `vmlinuz` has no `.sbat` section, like
  Fedora's (`CONFIG_EFI_SBAT_FILE=""` in both). shim accepts that today;
  [rhboot/shim#591](https://github.com/rhboot/shim/issues/591), which would refuse it,
  has been open since 2023.
- The G4 VM runs OVMF with Secure Boot variables and the key pre-enrolled. Whether
  `virt-fw-vars` can inject a MOK is checked in W3.
- **Way back:** turn Secure Boot off in the firmware. Nothing else changes.

### 8. The ALC294 quirk

- Decision 23 stands: the `model=` alias drop-in ships first, if it passes its rows
  (ARCHITECTURE §6.2). CachyOS carries Realtek quirks for other ASUS models, so the
  winner is checked again on this kernel. The CachyOS config keeps the HDA patch loader,
  `RECONFIG`, `HWDEP` and the ALC269 codec module, and G1 asserts them, so ADR 0004's
  patch firmware remains possible.
- The one-line `SND_PCI_QUIRK(0x1043, 0x1ab2, …)` to the working fixup goes upstream
  to tiwai/sound with the owner's Tested-by.
- The kernel lane carries that line as a patch only if the drop-in fails its rows. It
  is generated against the CachyOS tag tree, which has extra ASUS and Realtek quirks,
  and applied with fuzz 0. The bump report checks for the SSID, and the patch is
  dropped when the CachyOS tree has it. A quirk table changes often near any entry, so
  a carried patch may need a refresh on a kernel bump; that is why the drop-in comes
  first.
- The disabled patch is
  `packaging/pkgs/kernel/patches/0001-ALSA-hda-realtek-Fix-speaker-output-on-ASUS-M7400QC.patch`,
  out of `series` (its context fails on v7.3-rc4, review C12).

## Consequences

- The kernel leaves Fedora's signature and Bodhi's karma gating. Apex owns kernel
  security latency, within the limits of §4.
- Three third-party sources join the trust roots: CachyOS (the signed source tag), the
  COPR (the SRPM, including the config and BORE patch it fetches unpinned) and
  negativo17 (the kmod SRPM and the userspace binaries, which are NVIDIA's). Pinned
  keys, sha256 locks, mirrors and reviewed bumps are the mitigation. The userspace
  binaries are not rebuilt, so a compromised negativo17 key is caught only by review of
  lock bumps.
- No persistent module-signing key exists. A third Apex key comes only with Secure
  Boot, by the owner's decision.
- CachyOS carries scheduler, amd-pstate, ACPI idle and TSC patches, and turns split-lock
  mitigation off. Its regression surface is larger than Fedora's. The G4 VM exercises
  neither s2idle nor NVIDIA, so every new kernel line and every NVIDIA release needs a
  laptop run.
- The laptop builds its own kernel: 20–90 minutes about once a week, and once more per
  driver bump, on AC. A kernel regression that breaks KVM, suspend or storage also
  blocks the builder VM that would build the fix. The rollback deployment and
  `hold.txt` cover that.
- New kernel lines can break the NVIDIA modules before negativo17 adds a patch, while
  the old line reaches end of life about 16 days after the new one. The dGPU may then
  be off for a while (`degraded=nvidia`), by the owner's choice.
- Kernel suspend notifiers in the open modules are new: negativo17 uses them since
  March 2026. A suspend hang would need NVIDIA's suspend units back (§6).
- The first image with NVIDIA grows by about 330 MB compressed (about 1 GB installed,
  an estimate). A later kernel bump adds only the kmod, about 10 MB, if rechunking
  keeps the NVIDIA set in stable chunks.
- The image package is public (decision 20). The NVIDIA licence allows redistribution
  of the unmodified binaries with the licence, and `/usr/share/licenses/nvidia-driver/`
  ships it. The kernel and the open modules are GPL, so each public image digest gets a
  public source artifact: both SRPMs, the spec patches and the series. This is not
  legal advice.
- Crash analysis uses the `vmlinux` kept in the lane's store, because no debuginfo
  package exists.

## Alternatives rejected

- **Fedora's kernel, with the dGPU off or on nouveau with NVK.** The review's
  recommendation. The owner chose CachyOS and NVIDIA.
- **COPR's binary RPMs.** Their module key is COPR's, so the NVIDIA modules could not
  share it, `sig_enforce` would fail, and the modules would load tainted. No way to
  carry a patch. COPR's build hosts stay in the chain. It remains the fallback if K1
  shows the builder cannot sustain the builds.
- **`kernel-cachyos-lto` (Clang ThinLTO).** The owner chose GCC, and the NVIDIA modules
  must be built with the kernel's toolchain.
- **akmods or DKMS on the laptop.** The owner's rule; `/usr` is read-only anyway.
- **Universal Blue's akmods images.** They have no CachyOS flavour, and they would add
  another trust root.
- **RPM Fusion or NVIDIA's CUDA repository.** RPM Fusion's `xorg-x11-drv-nvidia` trips
  the legacy gate. NVIDIA documents only Fedora 44 and DKMS.
- **A persistent Apex MOK from the first build, its certificate built into every kernel
  through `CONFIG_SYSTEM_TRUSTED_KEYS`.** A driver bump would not rebuild the kernel,
  and the break-glass image could keep NVIDIA under Secure Boot. It was rejected: it
  adds a third persistent key before anything needs one (answer 21 keeps two), and its
  private half would meet third-party build code at every kmod build. The per-build
  key costs one warm kernel build a month.
- **The MOK alone, without a builtin certificate.** The kernel ignores MOKs with Secure
  Boot off, so the modules would load tainted and `sig_enforce` would fail. With Secure
  Boot on, it would need `mokutil --trust-mok`.
- **The 595 production branch.** negativo17 does not publish it, and building the
  userspace from NVIDIA's `.run` is L effort.
- **supergfxctl.** This model has no MUX and no dGPU switch.
- **A config delta (Zen 3 `-march`, TEO, RCU lazy on).** ADR 0005's tuning is not
  carried. RCU lazy and the scheduler switches are measured through kernel arguments
  and sysctls first.
